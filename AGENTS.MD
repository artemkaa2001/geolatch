GeoLatch - Complete Production Development Specification

ROLE AND OBJECTIVE

Ты - опытный Senior Linux Engineer, Security Engineer и Python Developer.

Твоя задача - с нуля создать полноценный open-source проект GeoLatch, готовый к реальному использованию на Linux-серверах.

Работа ведётся в новом пустом GitHub-репозитории.

GeoLatch - лёгкая утилита для управления географической блокировкой входящих сетевых соединений на Linux VPS с помощью nftables.

Главная идея: пользователь устанавливает программу одной командой, после чего автоматически открывается красивый интерактивный терминальный мастер. Пользователь выбирает IP-адреса сервера и страны, которым запрещён доступ. Программа безопасно применяет правила, автоматически обновляет GeoIP-базы и восстанавливает состояние после перезагрузки.

После установки пользователь может в любой момент выполнить:

geolatch

И попасть в полноценное интерактивное меню управления.

Весь интерфейс должен поддерживать два языка: русский и английский.

1. Базовые принципы разработки

Проект должен быть:

1. Бесплатным.
2. Open-source.
3. Лёгким.
4. Универсальным.
5. Надёжным.
6. Безопасным для удалённых VPS.
7. Полностью управляемым из терминала.
8. Удобным для новичков.
9. Пригодным для автоматизации.
10. Независимым от коммерческих GeoIP API.

Не создавай демон, который постоянно обрабатывает пакеты.

Фильтрацию выполняет ядро Linux через nftables. Python нужен только для управления конфигурацией, загрузки данных, генерации правил и пользовательского интерфейса.

Не используй веб-панель, PostgreSQL, Redis, Docker как обязательную среду или внешние SaaS.

Не используй платные API, обязательные токены или регистрацию.

Используй современные практики production development.

Код должен быть читаемым, модульным и поддерживаемым.

Не создавай абстракции ради абстракций.

Не пытайся уместить весь проект в один гигантский Python-файл.

Не оставляй критическую функциональность в виде TODO или заглушек.

Все заявленные возможности должны иметь реальную реализацию.

3. Установка одной командой

Нужно обеспечить установку из GitHub одной командой.

Пример:

git clone https://github.com/OWNER/geolatch.git && cd geolatch && sudo ./install.sh

"OWNER" должен быть заменён на фактического владельца репозитория в документации.

Главный установщик:

"install.sh"

Он должен выполнять всю работу без необходимости вручную запускать несколько скриптов.

Последовательность установки

1. Проверить Linux.
2. Определить дистрибутив.
3. Проверить права.
4. Проверить архитектуру.
5. Проверить Python.
6. Проверить наличие nftables.
7. Установить необходимые зависимости.
8. Создать изолированное Python-окружение.
9. Установить GeoLatch.
10. Создать необходимые директории.
11. Зарегистрировать глобальную команду "geolatch".
12. Установить необходимые systemd units.
13. Проверить успешность установки.
14. Автоматически запустить интерактивный мастер GeoLatch.

Пользователь не должен вручную запускать "geolatch setup" после установки.

Важно

Для установки предпочтительно использовать один "install.sh".

Но сама программа должна иметь нормальную модульную архитектуру.

Не использовать "curl | bash" как обязательный метод установки.

Не устанавливать Python-пакеты в системный Python с принудительным обходом externally-managed-environment.

Использовать virtual environment.

Установщик должен быть idempotent.

Повторная установка не должна уничтожать конфигурацию или изменять действующие правила без подтверждения.

При обнаружении существующей установки нужно предложить:

- Открыть GeoLatch.
- Обновить программу.
- Восстановить установку.
- Отменить операцию.

Обработка ошибок

Если установка завершилась ошибкой, пользователь должен увидеть конкретную причину.

Нельзя очищать экран раньше, чем человек успел прочитать ошибку.

Программа не должна сообщать об успешной установке, если исполняемый файл или необходимые системные компоненты не работают.

Не нужно разбрасывать русские и английские строки непосредственно по Python-модулям.

Создать централизованную систему переводов.

Например:

geolatch/
└── locales/
    ├── en.json
    └── ru.json

Или аналогичный формат.

Использовать стабильные translation keys:

menu.title
menu.settings
menu.firewall_status
setup.select_country
setup.select_ip
update.completed
error.invalid_config

Предусмотреть:

- Интерполяцию переменных.
- Форматирование количества элементов.
- Форматирование дат.
- Поддержку русского единственного и множественного числа.
- Корректное отображение Unicode.
- Fallback на английский при отсутствующем переводе.
- Проверку полноты переводов в тестах.

Не должно быть ситуаций, когда половина русскоязычного меню внезапно отображается на английском.

Названия стран также должны иметь русскую и английскую локализацию.

4.4. CLI и локализация

При запуске:

geolatch status

Вывод должен соответствовать выбранному языку.

Добавить возможность временно переопределить язык:

geolatch --lang en status

Это не должно изменять сохранённые настройки.

Машинные форматы вывода, если они предусмотрены, должны оставаться стабильными независимо от языка.

6. Полноценный интерактивный терминальный интерфейс

Это одно из главных требований.

GeoLatch не должен выглядеть как обычный Bash-скрипт с последовательными "read" и "echo".

Нужен полноценный TUI (Terminal User Interface).

Предпочтительно использовать Textual.

Если выбрана другая библиотека, объясни, чем она лучше для данного случая.

6.1. Full-screen interface

Интерфейс работает в полноэкранном режиме терминала.

Каждый шаг настройки должен открываться как отдельный экран.

При переходе предыдущий экран полностью заменяется новым.

В истории терминала не должны накапливаться старые вопросы и ответы.

Использовать alternate screen buffer.

Не строить основной интерфейс на бесконечных вызовах:

os.system("clear")

Вместо этого использовать нормальный рендеринг и управление жизненным циклом экранов.

Требования:

- Отсутствие визуального мусора.
- Отсутствие постоянного мерцания.
- Чистые переходы.
- Корректная обработка размера терминала.
- Корректная работа через SSH.
- Восстановление первоначального содержимого терминала при выходе.
- Восстановление курсора и терминальных режимов.

Если терминал не поддерживает полноценный TUI, должна быть понятная ошибка или ограниченный текстовый fallback.

6.2. Управление

Обязательные клавиши:

Клавиша| Действие
↑ / ↓| Перемещение

Esc| Назад
Q| Выход, где применимо
Ctrl+C| Корректное завершение
Tab| Перемещение фокуса

Все действия должны быть интуитивными.

Внизу каждого основного экрана показывать небольшую подсказку.

При смене языка подсказка должна переводиться.

При выходе с несохранёнными изменениями показывать подтверждение.

Не создавать гигантский логотип.

На очень маленьких терминалах показывать компактную версию или объяснять минимальный необходимый размер.

После установки GeoLatch автоматически запускает setup wizard.

Шаг 1. Выбор языка

Показать English / Русский.

Select network interfaces

[x] eth0       Public network
[ ] eth1       Private network
[ ] docker0    Docker bridge
[ ] tun0       VPN tunnel

Enter - Continue
Esc   - Back

Названия и категории демонстрационные.

Показать найденные адреса.

- Все публичные IP.
- Один конкретный IP.
- Несколько IP.
- IPv4.
- IPv6.

Пример:

Select destination IP addresses

[x] 203.0.113.10    eth0
[x] 203.0.113.20    eth0
[ ] 203.0.113.30    eth0
[ ] 2001:db8::10   eth0

Selected: 2 IP addresses

Адреса документационные.

Важно: программа фильтрует именно входящий трафик, адресованный выбранным IP-адресам сервера.

Не нужно блокировать входящие соединения на других IP, если пользователь их не выбирал.

Поддержать явный ввод адреса, если он не обнаружен автоматически.

Для такого адреса показывать предупреждение и выполнять дополнительные проверки.

Показать интерактивный список стран.

- Поиск по названию.
- Поиск по ISO-коду.
- Прокрутку.
- Множественный выбор.
- Счётчик выбранных стран.
- Выделение выбранного элемента.
- Возможность снять все отметки.

Пример:

Выберите страны для блокировки

Поиск: ир

[x] Иран               IR
[ ] Ирак               IQ
[ ] Ирландия           IE

Выбрано: 1 страна

На английском должны отображаться английские названия.

Не использовать для выбора только числовой ввод списка через запятую.

Основной интерфейс должен быть интерактивным.

Шаг 6. IPv4 и IPv6

Предложить:

- IPv4 only.
- IPv6 only.
- IPv4 + IPv6.

Не требовать IPv6, если у сервера нет подходящих IPv6-адресов.

Показывать понятное предупреждение, если выбранная IP-family недоступна.

Шаг 7. Источник GeoIP

Предложить:

1. ipverse Geo IP Blocks - Recommended.
2. ipverse Country IP Blocks - Compact.

Описать различия понятными словами.

Пользователь должен понимать, что компактная база может отличаться по точности и покрытию.

Шаг 8. Защита административного доступа

Проверить возможные риски потери SSH-подключения.

Предложить добавить доверенный административный IP/CIDR в allowlist.

Не предполагать, что SSH peer address обязательно совпадает с реальным публичным адресом администратора.

Предусмотреть безопасный тестовый режим применения с автоматическим rollback.

Шаг 9. Дополнительные политики

Пользователь должен иметь возможность создать дополнительные политики, например:

- IP 1: Iran, Pakistan.
- IP 2: China.
- IP 3: No blocking.

После создания первой политики предложить добавить следующую.

Не заставлять пользователя заново проходить весь первичный мастер, если он хочет настроить несколько IP с разными ограничениями.

9. Принцип географической блокировки

GeoLatch блокирует новые входящие подключения на выбранные destination IP по странам исходных IP-адресов.

Пример.

Сервер имеет:

203.0.113.10
203.0.113.20
203.0.113.30

Пользователь создаёт:

Policy 1:
Destination: 203.0.113.10
Blocked: IR, PK

Policy 2:
Destination: 203.0.113.20
Blocked: CN

Policy 3:
Destination: 203.0.113.30
Blocked: none

Результат:

- На первый IP новые подключения из IR и PK блокируются.
- На второй IP новые подключения из CN блокируются.
- Третий IP GeoLatch не ограничивает.
- Все остальные источники продолжают обработку обычными firewall-правилами Linux.

GeoLatch не должен выдавать глобальный ACCEPT, который мог бы обходить правила других firewall.

Важное ограничение: GeoIP - приблизительная классификация по IP-адресам. Она не гарантирует физическую страну пользователя.

10. Firewall backend: nftables

Использовать только nftables для первой версии.

Не реализовывать отдельные backend для iptables, IPsec или eBPF.

nftables достаточно для задачи.

Создать собственную управляемую таблицу, например:

table inet geolatch

GeoLatch должен изменять только принадлежащие ему объекты.

Категорически запрещено:

nft flush ruleset

Также запрещено глобально удалять чужие tables, chains или sets.

Не отключать UFW, Docker или системные firewall-сервисы.

10.1. Производительная фильтрация

Использовать nftables sets с CIDR.

Предпочтительно:

- "ipv4_addr"
- "ipv6_addr"
- "flags interval"
- Оптимизация пересекающихся CIDR.
- Минимальное число правил.

Не создавать по отдельному правилу на каждый IP-префикс.

Реализовать эффективную структуру для нескольких стран и нескольких destination IP.

Повторно использовать одинаковые source sets, если это уменьшает память и не усложняет безопасное обновление.

Не дублировать большую GeoIP-базу для каждого destination без необходимости.

10.2. Правильный netfilter hook

Нужно учитывать:

- Обычные серверные приложения.
- Nginx.
- HAProxy.
- Xray.
- Docker.
- DNAT.
- Published container ports.
- Несколько публичных IP.

Фильтрация должна проверять исходный destination IP до его возможного изменения через DNAT.

Исследовать и реализовать подходящий "prerouting" hook.

Рассмотреть priority "-150", то есть после conntrack и до стандартного dstnat, если это подтверждается архитектурой и тестами.

Обязательно проверить hook ordering на поддерживаемых ядрах.

Не ограничиваться INPUT-chain, если из-за этого Docker-трафик будет обходить фильтрацию.

Не блокировать чужой транзитный трафик.

Учитывать "iifname", destination address и состояние соединения.

10.3. Connection tracking

По умолчанию блокировать новые входящие соединения.

Режим сохранения established/related connections:

"preserve_established: true"

Не ломать ответы на исходящие подключения сервера.

Поддержать:

- TCP.
- UDP.
- IPv4.
- IPv6.

Корректно учитывать "ct state".

Не блокировать жизненно важные локальные сетевые протоколы, включая IPv6 Neighbor Discovery.

Предусмотреть диагностику окружений с "notrack" и нестандартными правилами conntrack.

10.4. Allowlist

Поддержать доверенные source IP/CIDR.

Allowlist должна исключать указанные источники только из географических ограничений GeoLatch.

Она не должна переопределять правила других firewall.

Не создавать глобальное правило "accept" ради реализации allowlist.

11. GeoIP-базы

GeoLatch должен использовать бесплатные обновляемые базы CIDR по странам.

Не обращаться к внешнему API на каждый сетевой пакет.

Не делать GeoIP lookup через Python во время обработки соединений.

11.1. Основной provider

Repository:

https://github.com/ipverse/geo-ip-blocks

Использовать его как основной источник.

Ожидаемые пути для IPv4/IPv6 необходимо проверить по актуальной структуре upstream.

Пример:

country/ir/ir-ipv4.txt
country/ir/ir-ipv6.txt

Проверить URL перед реализацией.

11.2. Альтернативный provider

Repository:

https://github.com/ipverse/country-ip-blocks

Использовать как компактный альтернативный источник на основе RIR.

Проверить фактическую структуру файлов.

11.3. Переключение источника

В настройках:

- ipverse-geo.
- ipverse-rir.

Разница должна быть понятна пользователю.

Не переключать источник автоматически при обычном сбое GitHub.

Источник задаётся конфигурацией.

11.4. MaxMind

Исследовать возможность использования GeoLite2 в будущем.

Но не делать MaxMind обязательным.

Официальное получение GeoLite2 требует аккаунта и лицензионного ключа, а распространение имеет дополнительные условия.

Не использовать случайные GitHub-зеркала без проверки лицензии.

Для MVP достаточно двух ipverse providers.

11.5. Лицензии

Проверить актуальные условия лицензирования используемых источников.

Указать источники и лицензии в документации.

Не считать MIT-лицензию самого приложения разрешением на любое распространение чужих баз.

Не включать сторонние GeoIP-данные в репозиторий, если условия этого не позволяют.

12. Обработка GeoIP

Реализовать отдельный provider layer.

При загрузке:

1. Получить список активных стран.
2. Определить нужные IP-family.
3. Скачать только необходимые базы.
4. Проверить HTTP status.
5. Проверить размер файлов.
6. Проверить формат содержимого.
7. Распарсить CIDR.
8. Нормализовать сети.
9. Удалить дубликаты.
10. Объединить пересекающиеся и соседние диапазоны.
11. Выполнить проверки аномалий.
12. Сохранить проверенный результат.

Использовать HTTPS.

Применять timeouts, retries и backoff.

Не считать HTTP 200 подтверждением корректности базы.

Не принимать HTML вместо CIDR.

Не применять пустые списки вместо ранее существовавших непустых.

Записывать SHA-256 скачанных данных.

Хеш нужен для контроля изменений и локальной целостности, но сам по себе не доказывает подлинность удалённого источника.

12.1. Валидация

Использовать стандартный Python "ipaddress" или проверенную библиотеку.

Проверять:

- CIDR.
- IPv4/IPv6.
- Некорректные адреса.
- Дубликаты.
- Overlapping networks.
- Неожиданные служебные диапазоны.
- Неожиданные default routes.
- Пустые или повреждённые списки.

Записи вроде:

0.0.0.0/0
::/0

Не должны незаметно попадать в GeoIP sets и блокировать весь интернет.

12.2. Anomaly detection

Нужна защита от повреждённых или аномальных обновлений.

Проверять:

- Резкое уменьшение списка.
- Резкое увеличение списка.
- Сильное изменение адресного покрытия.
- Пропажу страны.
- Необычное изменение размера.
- Некорректное содержимое.

Количество CIDR не может быть единственным критерием, поскольку агрегирование сетей меняет количество префиксов без аналогичного изменения покрытия.

Использовать разумные пороги и корректную обработку маленьких стран.

Если данные подозрительны, обновление отклоняется, а предыдущая база остаётся активной.

13. Конфигурация

Основной конфигурационный файл:

/etc/geolatch/config.yaml

Использовать YAML.

Пример:

version: 1

language: ru

source: ipverse-geo

updates:
  enabled: true
  interval: daily

network:
  ipv4: true
  ipv6: true
  interfaces:
    - eth0

firewall:
  action: drop
  preserve_established: true

allowlist:
  ipv4:
    - 198.51.100.50/32
  ipv6: []

policies:
  - name: primary
    enabled: true
    destinations:
      - 203.0.113.10
    block_countries:
      - IR
      - PK

  - name: secondary
    enabled: true
    destinations:
      - 203.0.113.20
    block_countries:
      - CN

Все IP являются документационными.

Можно улучшить схему, если это необходимо для корректной архитектуры.

Требования:

- Несколько независимых policies.
- ISO 3166-1 alpha-2.
- IPv4/IPv6.
- All destinations.
- Explicit destinations.
- Allowlist.
- Валидация.
- Версионирование формата.
- Читаемые сообщения об ошибках.
- Безопасная миграция конфигурации.

13.1. Режим all

Поддержать:

destinations: all

Это должно означать все подходящие публичные локальные адреса на выбранных интерфейсах.

Не трактовать all как глобальный запрет на произвольный forwarded traffic.

Обрабатывать изменение адресов после reboot и при повторном применении конфигурации.

Если поддерживается автоматическое отслеживание изменения адресов в работающей системе, реализовать его через аккуратную event-driven интеграцию.

Если такого отслеживания нет, честно документировать, когда необходимо повторное применение правил.

13.2. Конфликты

Политики для одного destination должны иметь определённую семантику.

Предпочтительно объединять блокируемые страны.

Некорректные и неоднозначные комбинации должны отклоняться валидатором.

15. Атомарное применение правил

Это критически важная часть проекта.

Нельзя реализовывать обновление следующим образом:

1. Удалить прежние правила.
2. Начать скачивание данных.
3. Добавлять новые сети по одной.
4. При ошибке оставить firewall с частичной конфигурацией.

Правильная последовательность:

1. Скачать все необходимые файлы.
2. Проверить их.
3. Подготовить объединённые списки.
4. Проверить аномалии.
5. Подготовить новый ruleset.
6. Проверить его синтаксис через nftables.
7. Подготовить snapshot прежнего состояния.
8. Применить изменение как атомарную транзакцию.
9. Проверить фактическое состояние.
10. Сохранить новое состояние как confirmed.
11. При ошибке восстановить last-known-good.

Использовать возможности nftables atomic transactions.

Реализовать безопасное обновление sets.

Избегать промежутков, когда действующий набор оказывается пустым или частично заполненным.

Проверить доступность нужных операций на поддерживаемых версиях nftables.

Не полагаться на неподдерживаемые операции.

16. Safe Apply и SSH Rollback

GeoLatch будет использоваться на VPS через SSH.

Поэтому неправильно настроенный firewall не должен необратимо блокировать администратору доступ.

Реализовать safe apply.

Процесс:

1. Сохранить подтверждённое состояние.
2. Подготовить восстановление.
3. Применить новые правила.
4. Запустить независимый rollback watchdog.
5. Попросить подтверждение, если это интерактивная операция.
6. При подтверждении отменить rollback.
7. При отсутствии подтверждения восстановить прежнее состояние.

Rollback должен работать даже при аварийном завершении основного Python-процесса.

Не полагаться только на "finally".

Рассмотреть systemd transient service или другое надёжное средство.

Подтверждение не должно считаться успешным только потому, что процесс не завершился.

Предусмотреть ручной аварийный откат.

Для unattended update использовать отдельный безопасный сценарий с проверками и восстановлением прежних данных при ошибке.

В README честно описать ограничения safe apply: он не может гарантировать доступность SSH при любой внешней сетевой проблеме или при конфликтах с чужим firewall.

17. Автоматические обновления

По умолчанию GeoIP обновляется один раз в сутки.

Использовать systemd timer.

Файлы:

geolatch-update.service
geolatch-update.timer

Использовать:

OnCalendar=daily
Persistent=true
RandomizedDelaySec

Таймер должен запускать короткую CLI-операцию и завершаться.

Не нужен постоянно работающий Python daemon.

При ошибке загрузки:

- Оставить старую базу.
- Оставить старые rules.
- Записать ошибку.
- Не очищать sets.
- Не останавливать firewall.
- Повторить попытку при следующем запуске.

Не применять частичное обновление отдельных стран, если остальные необходимые данные не прошли проверку.

Если база не изменилась, не перезагружать правила без причины.

Поддержать ручное обновление из TUI.

Использовать блокировку конкурентных операций, чтобы "update", "apply" и "rollback" не конфликтовали.

18. Persistence после перезагрузки

После reboot GeoLatch должен восстанавливать последнюю подтверждённую конфигурацию без доступа к интернету.

Создать systemd restore unit.

Например:

geolatch-restore.service

Он должен:

- Проверять сохранённое состояние.
- Применять last-known-good.
- Не скачивать данные во время обязательного восстановления.
- Не уничтожать чужие правила.
- Корректно взаимодействовать с nftables.service.
- Учитывать systemd ordering.
- Учитывать наличие UFW и Docker.

Не изменять глобальный nftables.service без необходимости.

Обязательно протестировать сценарий reboot.

Если полноценный reboot-test невозможен в текущем окружении, предоставить тестируемый restore workflow и честно указать отсутствие проверки на реальном reboot.
